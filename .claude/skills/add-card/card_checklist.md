# 卡片規則問題清單

起草 `backend/cards.yaml` 時逐題回答。每一題都要寫出**答案的出處**(官網條款網址加段落名稱,或爬蟲檔中的列);爬蟲資料只能回答「有哪些方案、幾 %、點名哪些店」,其餘幾乎都要看條款。找不到出處的題目標成「待確認」,交給人決定,**不要猜**。

欄位的完整語法見 `backend/cards.yaml` 開頭的註解;規則的設計理由見 `docs/DB_DESIGN.md` 第 6、7 節。

## 0. 先判斷這張卡像哪一張

現有三張卡代表三種回饋方式,從最像的那張開始改,比從零寫穩:

| 範本 | 回饋方式 | 特徵 |
|---|---|---|
| CUBE卡 `cathay_cube` | **切換方案型** | 有等級;同時只有一個權益方案有效,要切換;方案數字不含基本回饋,也不疊加 |
| 吉鶴卡 `ubot_jiho` | **常態加碼型** | 沒有等級;所有指定類別同時有效,不用切換;數字已含基本回饋;有卡片層級加碼 |
| Unicard `esun_unicard` | **選方案 + 疊加型** | 依使用者選的方案決定回饋率;特店回饋要加上一般消費;任意選要挑店 |

## 1. 基本資料

| 問題 | 欄位 | 注意 |
|---|---|---|
| 卡片代號 | `cards.<card_id>` | 小寫英文加底線,`銀行_卡名`,例如 `taishin_richart`。存進使用者資料,**定了就不能改** |
| 顯示名稱、銀行 | `name`、`bank` | |
| 爬蟲中的卡名 | `crawl_name` | 跟爬蟲的 `card_name` 一字不差 |
| 卡片層級的提醒 | `notes` | 現有三張卡都有「實際回饋依當期公告為準」 |

## 2. 回饋率由什麼決定

| 問題 | 欄位 | 範例 |
|---|---|---|
| 同一個方案,回饋率會因為什麼設定而不同? | `rate_by` | 等級 → `level`(CUBE);使用者選的方案 → `plan`(Unicard);都一樣 → `null`(吉鶴卡) |
| 有哪些選項? | `settings.level` / `settings.plan` | 要跟爬蟲的 `card_level` 一字不差 |

爬蟲的 `card_level` 有幾種值,通常就是答案;但要用條款確認那是「等級」還是「使用者可以自己選的方案」。

## 3. 使用者要設定的開關

| 問題 | 欄位 | 範例 |
|---|---|---|
| 回饋要不要符合使用者自己的狀態? | `settings.toggles` | 童樂匯會員、新戶、電子帳單、自動扣繳 |
| 開關在畫面上叫什麼? | `toggles` 的值 | 用使用者看得懂的說法,例如吉鶴卡把「新戶並設定自動扣繳」寫成「新戶自動扣繳」 |

系統自己判斷的條件不用開關:目前只有 `birthday_month`(依使用者生日)。

## 4. 每個方案

爬蟲每個 `scheme_name` 都要決定:放進 `schemes`,還是放進 `skip_crawl_schemes` 並寫原因(例如「改由 general 設定」)。

| 問題 | 欄位 | 範例 |
|---|---|---|
| 要先做什麼才能拿到?(切換方案、登錄) | `action` | `需切換至樂饗購權益方案`;不用做任何事就省略 |
| 要符合哪些開關或條件? | `requires` | `[kids_club]`、`[birthday_month]` |
| 爬蟲的數字含不含基本回饋?要不要加上一般消費? | `stacks_with_general` | Unicard 百大特店 `true`;吉鶴卡已含、CUBE 不疊加 → 省略 |
| 涵蓋整個分類或國外,不只點名的店? | `covers` | 樂饗購 `{category: dining, country: TW}`;趣旅行 `{overseas: true}` |
| 只算使用者挑的店? | `pick_merchants_when_plan` + `settings.max_chosen_merchants` | Unicard 任意選,最多 8 家 |
| 用行動支付付款也算? | `payment_methods` | 爬蟲中標成 `payment_method` 的列;只限國內的店 |
| 要提醒使用者的限制 | `notes` | `需於週一至週五並滿足指定額度…` |

`covers` 的 `category` 要用資料庫中已有的分類(`dining`、`hotel`、`travel`…,查 `SELECT DISTINCT primary_category FROM merchants`)。爬蟲中標成 `category` 的列(國家、整類消費)是判斷 `covers` 的線索。

**「疊加」最容易錯**,一定要從條款確認:條款寫「加碼 X%」通常要疊加,寫「最高 X%」「回饋 X%(含基本回饋)」通常不疊加。拿條款中的計算範例驗證。

## 5. 一般消費

| 問題 | 欄位 | 範例 |
|---|---|---|
| 一般消費幾 %? | `general[].rate` | |
| 國內外不同嗎? | `general[].where` | `domestic`、`overseas`、國別代碼 `JP` |
| 依開關不同嗎? | `general[].requires` | Unicard:沒有開關 0%、電子帳單 0.3%、兩個都有 1% |
| 爬蟲中對應哪一列? | `general[].crawl_name` | 匯入時拿來比對數字 |

至少要有一層。各層取「條件和地點都符合」的最高一層。

## 6. 卡片層級加碼

| 問題 | 欄位 | 範例 |
|---|---|---|
| 有沒有符合條件就額外加 % 的?加在哪些方案或一般消費層上? | `bonuses` | 吉鶴卡新戶 `+0.5`,只加在國內一般消費與國內日系特店 |

## 7. 目前的模型表達不了的規則:遇到就停

條款中出現下面任何一種,**不要硬塞進現有欄位**,停下來告訴人「這張卡需要修改計算程式」,並說明是哪一條、影響哪些方案:

- 每月或每期的回饋上限(例如「每月最高回饋 300 元」)
- 要先登錄才有回饋、名額限制
- 滿額門檻(例如「單筆滿 1,000 元」)
- 只限特定日期或星期(寫進 `notes` 提醒可以,但計算時不會判斷)
- 依付款方式不同(感應、線上、分期)而不同,且不是行動支付綁卡
- 依消費金額分級的回饋率
- 需要使用者在 App 外的其他狀態(例如帳戶餘額、存款等級),而且不能用一個開關表示

只是 `notes` 能說清楚、不影響計算的限制,寫進 `notes` 即可。

## 8. 交給人確認時的格式

把答案整理成表,每一列一題,附出處;再附上起草好的 `cards.yaml` 段落。例如:

| 題目 | 答案 | 出處 |
|---|---|---|
| 範本 | 選方案 + 疊加型(像 Unicard) | |
| rate_by | `plan`:簡單選 / 任意選 / UP選 | 爬蟲 card_level;條款「權益方案」段落 |
| 百大特店要疊加一般消費嗎 | 要 | 條款範例「任意選 2.5% + 一般消費 1% = 3.5%」 |
| 新戶加碼 | **待確認**:條款寫「新戶最高 +1%」,沒說加在哪些消費 | 條款第 3 條 |
