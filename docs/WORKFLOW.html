1系統架構 已確定

資料分成兩種:爬蟲資料與使用者資料存在 MySQL;卡片規則(條件、疊加、挑店、一般消費)寫在 cards.yaml,後端啟動時讀進來。App 不直接碰資料庫,只送出「查哪家店」,拿回推薦結果。

2使用者流程

  1. 註冊 / 登入

    註冊填 email、密碼、姓名、生日;生日用來判斷慶生月。登入成功後,後端發一個 token,App 之後每次查詢都帶著它,後端靠它認出是誰。

    登入失敗一律顯示「帳號或密碼錯誤」,旁邊放「前往註冊」。

    已確定

  2. 設定我的卡片

    選卡 → CUBE 選等級、Unicard 選方案 → 打開需要的開關(童樂匯、新戶、電子帳單、自動扣繳)→ Unicard 任意選要挑店。每張卡有哪些選項,由後端告訴 App。

    設定存成這張卡的 config。先寫進資料庫,成功了才更新手機上的副本。

  3. 搜尋店家

    打第一個字就出現建議,支援別名(打「小七」會出現 7-11)。可以點建議,也可以直接按搜尋。

  4. 看推薦結果

    每張卡的最佳回饋,依 % 由高到低列出,附上要做的動作(例如「需切換至樂饗購權益方案」)與限制。查無此店時提示「以一般消費計算」。

3搜尋店家 已確定

自動補全和「確定是哪一家店」是兩件事:前者回多筆候選讓使用者挑,後者只回一家或找不到。使用者點了建議就直接拿到店家編號,不用再解析;沒點、直接按搜尋時,才拿輸入文字去比對。

4回饋怎麼算 已確定

計算分兩段。SQL 只負責撈資料,規則判斷全部交給後端 Python,因為疊加、挑店、多條件這些規則寫在 SQL 裡會很難讀、很難測,而撈出來的資料最多幾十筆,用 Python 判斷非常快。

SQL 撈資料

  • 使用者的卡片與 config、生日
  • 這些卡的所有方案、各等級/方案的回饋率
  • 這家店有沒有被方案點名、例外回饋率

Python 依 cards.yaml 判斷

  • 條件滿不滿足(含生日月)
  • 分類涵蓋、任意選有沒有挑這家
  • 疊加、每張卡取最高、卡片排序

每張卡各自走完下面七步,得出這張卡在這家店的最佳回饋。右欄用同一個例子一路走下去。

  1. 例子

    使用者持有 CUBE 和 Unicard,搜尋「台北101」。這個月不是他的生日月。

    卡片狀態 CUBE:Level 2,沒有勾任何條件 Unicard:任意選,有電子帳單和自動扣繳,挑的店裡有台北101

  2. 拿出卡片狀態與地點

    從這張卡的 config 讀出等級或方案、打開的開關,再加上系統自動算出的條件:本月是否為生日月(用 users.birthday 比對)。

    另外看店家在國內還是國外(店家的國別);找不到店家時當作國內。

    新規則 生日月條件、國內外

    這個例子 CUBE:Level 2;條件 — 無;生日月 — 否 Unicard:任意選;條件 — 電子帳單、自動扣繳 台北101 在國內

  3. 依條件篩掉方案

    方案要求的條件全部滿足才保留。一個方案可以要求不只一個條件(Unicard 的 1% 要電子帳單和自動扣繳同時成立)。

    新規則 一個方案可要求多個條件

    這個例子 CUBE 童樂匯(沒加入童樂匯) CUBE 慶生月(不是生日月) Unicard 一般消費 0%、0.3%、1% 三層都保留(條件都滿足)

  4. 判斷方案適不適用這家店

    兩種情況之一就適用:店被方案點名,或店在方案涵蓋的範圍內。樂饗購涵蓋國內所有餐廳;趣旅行涵蓋飯店、旅行類(高鐵、旅行社、叫車)與所有國外的店。

    Unicard 任意選另外要求:百大特店只適用使用者挑過的店(最多 8 家)。

    新規則 涵蓋範圍可限國內或涵蓋國外、任意選挑店

    這個例子 CUBE 樂饗購:台北101 被點名 ✓ Unicard 百大特店:被點名,而且使用者挑過 ✓

  5. 取回饋率

    方案在使用者等級或方案下的回饋率;少數店有例外回饋率(例如童樂匯有些店 10%),有例外就用例外。

    一般消費依條件和國內外分層,取符合的最高一層。例如 CUBE 國內 0.3%、國外的店 2.5%。

    新規則 一般消費分國內外

    這個例子 CUBE 樂饗購 Level 2:3% CUBE 一般消費:0.3%(國內,海外 2.5% 不適用) Unicard 百大特店 任意選:2.5% Unicard 一般消費:0% / 0.3% / 1%,取最高 1%

  6. 疊加與加碼

    疊加:Unicard 百大特店的回饋率要加上一般消費(爬蟲數字不含基本回饋)。

    加碼:吉鶴卡的新戶自動扣繳 +0.5%,只加在國內一般消費和國內日系特店。吉鶴卡爬蟲數字本身已含基本 1%,不再疊加。

    新規則 疊加、卡片加碼

    這個例子 Unicard 百大特店:2.5% + 1% = 3.5% CUBE 樂饗購不疊加,維持 3%

  7. 每張卡取最好的一筆

    一般消費和所有適用的方案一起比,取最高。同分時優先不用做任何動作的(一般消費),其次是點名這家店的方案。

    一起比是因為一般消費有時比較高:CUBE Level 1 在國外的店,趣旅行 2%、海外消費 2.5%,應該推薦不用切換的 2.5%。

    這個例子 CUBE:3% 對 0.3% → 3%,樂饗購(需切換至樂饗購權益方案) Unicard:3.5% 對 1% → 3.5%,百大特店

  8. 卡片排序

    依回饋率由高到低,同分依卡名排。使用者持有的每張卡都會列出。

    這個例子 1. Unicard 3.5% 　2. CUBE 3%

8規則與設定怎麼存 已確定

「規則」和「設定」是兩種東西,分開存:

卡片規則 → cards.yaml

每個使用者都一樣,只有一份
  • CUBE 有哪些等級、Unicard 有哪些方案、各卡有哪些開關
  • 童樂匯要加入才算、慶生月要生日月
  • 樂饗購涵蓋所有餐廳
  • 百大特店會疊加一般消費,任意選要挑店
  • 各卡的一般消費

放在 repo,有 git 紀錄。改規則 = 改檔案、重啟後端。

使用者設定 → user_cards.config

每個人不同,存在資料庫
  • 我的 CUBE 是 Level 幾
  • 我的 Unicard 選哪個方案、挑了哪幾家店
  • 我有沒有加入童樂匯、是不是新戶、有沒有電子帳單和自動扣繳

MySQL 的 JSON 欄位。不同卡的設定欄位不同,不用為每張卡加欄位或加表。

config 長這樣

卡片config
CUBE{"level": "Level 2", "kids_club": false}
吉鶴卡{"new_customer": true}
Unicard{"plan": "任意選", "e_bill": true, "auto_debit": true, "chosen_merchants": [12, 87]}

資料庫只檢查「是不是合法的 JSON」,內容由後端依 cards.yaml 檢查,不合法就拒絕儲存:等級或方案必須在選項內(擋掉 level_1 這種拼錯的值)、只能有定義過的開關、chosen_merchants 只有任意選才能有、最多 8 家,而且每家店都必須在百大特店名單上。

cards.yaml 大概長這樣

# 示意,欄位名稱以實作為準。完整範例見 docs/DB_DESIGN.md 6.2
cards:
  cathay_cube:
    name: CUBE卡
    rate_by: level                          # 回饋率由「等級」決定
    settings:
      level: [Level 1, Level 2, Level 3]
      toggles: { kids_club: 童樂匯 }         # 開關與畫面上的名稱
    schemes:
      樂饗購:
        action: 需切換至樂饗購權益方案
        covers: [{ category: dining, country: TW }]     # 國內所有餐廳
      趣旅行:
        action: 需切換至趣旅行權益方案
        covers: [{ category: hotel }, { category: travel }, { overseas: true }]
      童樂匯: { action: 需切換至童樂匯權益方案, requires: [kids_club] }
      慶生月: { action: 需切換至慶生月權益方案, requires: [birthday_month] }
    general:
      - { name: 一般消費, rate: 0.3 }
      - { name: 海外消費, rate: 2.5, where: overseas }   # 國外的店,不用切換

  esun_unicard:
    name: Unicard
    rate_by: plan                           # 回饋率由「方案」決定
    settings:
      plan: [簡單選, 任意選, UP選]
      toggles: { e_bill: 電子帳單, auto_debit: 自動扣繳 }
      max_chosen_merchants: 8
    schemes:
      百大特店:
        stacks_with_general: true           # 加上一般消費
        pick_merchants_when_plan: [任意選]   # 任意選只算挑過的店
    general:                                # 取符合條件中最高的
      - { name: 一般消費, requires: [],                   rate: 0 }
      - { name: 一般消費, requires: [e_bill],             rate: 0.3 }
      - { name: 一般消費, requires: [e_bill, auto_debit], rate: 1.0 }

  ubot_jiho:
    name: 吉鶴卡
    rate_by: null
    settings:
      toggles: { new_customer: 新戶自動扣繳 }
    schemes:                                # 爬蟲數字已含基本回饋,不疊加
      國內人氣餐廳: { notes: [需於週一至週五並滿足指定額度…] }
      國內日系特店: {}
      日本熱門商店: {}
    general:
      - { name: 國內一般消費, rate: 1.0, where: domestic }
      - { name: 國外一般消費, rate: 1.0, where: overseas }
      - { name: 日本消費,     rate: 2.5, where: JP }
    bonuses:
      - { requires: [new_customer], add: 0.5, applies_to: [國內一般消費, 國內日系特店] }

店家名單和各方案的回饋率來自爬蟲,存在資料庫,不寫在這裡。cards.yaml 只管規則。
