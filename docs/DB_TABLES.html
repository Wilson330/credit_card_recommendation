全貌與關聯

資料庫只存兩種東西:爬蟲來的資料(店家、方案、回饋率、點名店家)和使用者的資料(帳號、持有的卡)。卡片規則,例如誰要疊加、哪個方案涵蓋所有餐廳、一般消費幾 %,都不在資料庫,寫在 backend/cards.yaml。

三個共通原則

名稱比對一律先正規化

去頭尾空白、轉小寫、移除半形和全形空白。資料庫用產生欄位自動算出 normalized_name、normalized_alias,後端對使用者輸入套用同一規則,兩邊才比得起來。

"7 - ELEVEN " → "7-eleven"

定序統一 unicode_ci

所有表都用 utf8mb4_unicode_ci(不分大小寫)。後端連線也要指定同一個定序,否則 MySQL 8 預設的 0900_ai_ci 會跟欄位衝突,出現 Illegal mix of collations。唯一例外是爬蟲原名,用逐字元比對的 utf8mb4_bin。

編號不變,店家不刪

資料庫是正本,不再清空重灌,所以 merchant_id、scheme_id 分配後就固定。方案和使用者挑的店都記編號,店名可以放心改。店家停業時把 active 設 0,不刪除,舊的編號永遠有效。

店家

店家:3 張表

一家店只有一筆 merchants。它可能有好幾種叫法,分兩張表存:使用者會打的叫法放 merchant_aliases,比對時寬鬆、要的是找得到;爬蟲寫的原始店名放 merchant_source_names,比對時一字不差、要的是不會對錯。

merchants 438 家店

店家目錄。搜尋的對象,也是方案點名和推薦計算的對象。

欄位型別說明
merchant_idPKINT UNSIGNED 自動遞增店家編號。其他表和 user_cards.config 都用它指向店家。
nameUNIQUEVARCHAR(255)顯示名稱,也是搜尋比對的主名稱。可以隨時改,不影響回饋計算。不能重複,所以同品牌在不同國家要用名字區分,例如「日本 7-ELEVEN」。
normalized_nameINDEX產生欄位 STORED由 name 自動算出,搜尋用。不能手動寫入,改 name 時自動更新。
primary_categoryINDEXVARCHAR(50)主分類,目前 15 種。會影響回饋:樂饗購涵蓋國內所有 dining,趣旅行涵蓋 hotel、travel。分錯就會拿到不該拿的回饋。
countryVARCHAR(10)TW、JP,或在很多國家都有據點的 global。不是 TW 就算國外,決定海外一般消費和趣旅行涵蓋。
activeTINYINT(1)1 = 上架,0 = 停用。停用的店搜尋不到,但編號保留。
created_at / updated_atTIMESTAMP建立和最後修改時間,自動維護。

爬蟲回饋資料

爬蟲回饋資料:3 張表

一個方案是「某張卡在某類消費給的回饋」,例如 CUBE 的樂饗購、Unicard 的百大特店。資料庫只存爬蟲抓得到的事實:有哪些方案、各等級幾 %、點名了哪些店。方案的規則,例如要不要切換、涵蓋哪些分類、是否疊加一般消費,寫在 cards.yaml。

使用者

使用者:2 張表

註冊時只寫 users;登入後新增卡片時才寫 user_cards。下面的範例資料都是虛構的。

一次查詢用到哪些表

例子:使用者持有 CUBE(Level 2)和 Unicard(任意選、電子帳單、自動扣繳,挑了台北101),在 App 打「台北101」。

  1. 自動補全

    merchantsmerchant_aliases

    用正規化後的輸入比對店名和別名,完全相同的排最前面,再來是開頭相同、包含;同一級時台灣的店優先、名字短的優先。最多回 10 家,這裡回傳 #54 台北101。

  2. 讀使用者的卡

    usersuser_cards

    從 token 取出使用者編號,讀出生日和兩張卡的 config。

  3. 撈方案與回饋率

    card_schemesscheme_ratesscheme_merchants

    一條 SQL 撈出這兩張卡所有方案的所有等級回饋率,並用 LEFT JOIN 標出台北101 有沒有被點名:

    SELECT s.card_id, s.scheme_name, sr.variant, sr.reward_rate,
       (sm.merchant_id IS NOT NULL) AS is_named, sm.rate_override, sm.notes
FROM card_schemes s
JOIN scheme_rates sr ON sr.scheme_id = s.scheme_id
LEFT JOIN scheme_merchants sm
       ON sm.scheme_id = s.scheme_id AND sm.merchant_id = 54   -- 台北101
WHERE s.card_id IN ('cathay_cube', 'esun_unicard');
    結果(SQL 會回傳所有等級,這裡只列使用者的 Level 2 和任意選)
    card_idscheme_namevariantreward_rateis_named
    cathay_cube全支付Level 22.000
    cathay_cube台塑家Level 22.000
    cathay_cube慶生月Level 210.000
    cathay_cube樂饗購Level 23.001
    cathay_cube玩數位Level 23.000
    cathay_cube童樂匯Level 25.000
    cathay_cube趣旅行Level 23.000
    cathay_cube集精選Level 22.000
    esun_unicard百大特店任意選2.501

  4. Python 依 cards.yaml 判斷

    backend/cards.yaml

    SQL 只撈資料,規則全部在後端判斷:沒被點名、也不在分類涵蓋範圍內的方案丟掉;Unicard 百大特店確認使用者挑過台北101,再疊加一般消費 1%;每張卡跟一般消費一起比,取最高。結果是 Unicard 3.5%(百大特店)、CUBE 3%(樂饗購,需切換至樂饗購權益方案)。

匯入時寫哪些表

Allen 出新的爬蟲匯出檔時,用 python -m backend.importer 匯入。

資料表匯入時怎麼處理
merchant_source_names用爬蟲店名逐字查。查不到的列入報告,附「可能是既有店家」的建議,由人用 --map、--new、--ignore 處理。
merchants只在人用 --new 確認是新店時新增。匯入工具不會自己新增店家,因為它分不出新店和舊店改名。
card_schemes方案名稱要先在 cards.yaml 裡有,才會建立;沒有的方案這次略過。
scheme_rates每個方案在每個等級,取多數店家的回饋率當方案回饋率。
scheme_merchants重寫這次出現的方案的點名店家;回饋率和方案不同的店記進 rate_override。沒出現在這次匯出檔的方案保留不動。
users、user_cards不動。

匯入或人工修改後,要重新匯出 db/seed.sql 並 commit,別的機器才拿得到同樣的資料。人工修改另外寫成 SQL 檔放在 db/changes/,留下修改紀錄。步驟見 db/README.md。

不在資料庫裡的東西

東西放在哪原因
卡片定義、等級與方案選項、開關名稱cards.yaml規則每個使用者都一樣,放在 repo 有 git 紀錄,改了重啟後端就生效。
方案規則:要做的動作、條件、分類涵蓋、疊加、挑店cards.yaml這些規則寫在 SQL 裡很難讀、很難測。
一般消費回饋率、卡片加碼cards.yaml爬蟲沒有可靠的一般消費資料,由人維護。
登入 token不存token 自帶使用者編號和到期時間,由後端簽名,驗證簽名即可,不用查表。
